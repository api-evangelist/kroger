# Kroger

> The Kroger Co. operates a two-tier API programme from developer.kroger.com. Public APIs
> (Products, Locations, Identity, Cart, Authorization) are self-service after registration and
> carry published daily call quotas. Partner APIs (Carts, Catalog, Catalog V2, Identity,
> Locations, Products, Seamless Delivery, Locker Integration, Authorization) require a signed
> partner agreement. Everything is protected by OAuth 2.0 at api.kroger.com.

Generated by API Evangelist on 2026-08-27 from Kroger's own published documentation.
Kroger does NOT publish an llms.txt: https://developer.kroger.com/llms.txt returns HTTP 200
with a 790,646-byte HTML shell (soft 404). This file is API Evangelist's summary of Kroger's
public surface, not a Kroger document.

## Hosts

- Production API base: https://api.kroger.com/v1/
- Certification (test) API base: https://api-ce.kroger.com/v1/
- Developer portal: https://developer.kroger.com/
- Support: APISupport@kroger.com

## Authentication

All APIs use OAuth 2.0 bearer tokens. There is no API key.

- Token endpoint: https://api.kroger.com/v1/connect/oauth2/token
- Authorize endpoint: https://api.kroger.com/v1/connect/oauth2/authorize
- Grants: client_credentials (app data), authorization_code (customer data, PKCE available),
  refresh_token (single-use rotation, six-month life)
- Client authentication: HTTP Basic, base64(client_id:client_secret)
- Access tokens expire in 1800 seconds. Send as `Authorization: Bearer {token}`.
- Scopes are assigned by Kroger at app registration and CANNOT be self-expanded.
  Documented scopes: product.compact, product.full.read, product.personalized,
  cart.basic:rw, profile.full, coupon.basic.
- No OIDC, no RFC 8414/9728 metadata, no dynamic client registration — all probed 404.

Docs: https://developer.kroger.com/documentation/public/security/guides-oauth

## APIs

- [Products API](https://developer.kroger.com/documentation/api-products/public/products/overview):
  GET /v1/products (search by filter.term/filter.brand/filter.productId),
  GET /v1/products/{productId}. Supply filter.locationId to get price, fulfillment,
  aisle location and stockLevel — they are omitted without it.
- [Locations API](https://developer.kroger.com/documentation/api-products/public/locations/overview):
  /v1/locations, /v1/chains, /v1/departments — list, details and HEAD-query for each.
  Not paginated; default limit 9999, default radius 10 miles.
- [Identity API](https://developer.kroger.com/documentation/api-products/public/identity/overview):
  GET /v1/identity/profile — profile id only on the Public tier; full profile and loyalty
  card number on the Partner tier.
- [Cart API](https://developer.kroger.com/documentation/api-products/public/cart/overview):
  Public tier publishes ONE operation, add-to-cart. The Partner Carts API adds
  POST/PUT/DELETE on /v1/carts/{cartId}/items/{upc}.
- Partner-only: Catalog API, Catalog API V2, Seamless Delivery API, Locker Integration APIs.

## Rate limits (published, per endpoint, per day, shared across ALL clients)

- Products: 10,000
- Cart: 5,000
- Identity: 5,000
- Locations: 1,600 per endpoint (three endpoints)
- Partner APIs: no rate limit
- Window resets 24 hours after the client's first call to that endpoint.
- No rate-limit response headers are documented and 429 is absent from the published
  status-code table — a client cannot read its remaining budget from a response.

## Conventions

- All responses are JSON: `{ "data": ..., "meta": { "pagination": { start, limit, total } } }`
- Query filters are namespaced `filter.<field>`; pagination via filter.limit / filter.start
- Versioning is in the URI path (/v1/). No public deprecation or versioning policy.
- No idempotency keys, no dry-run mode, no request-id header.
- Two error envelopes: `{error, error_description}` for auth failures and
  `{errors:{timestamp, code, reason}}` for API failures. Not RFC 9457.

## Testing

Certification environment at https://api-ce.kroger.com/v1/ requires its own separate app
registration; an app's environment cannot be changed after registration. CE has NO customer
accounts, so Identity and Cart must be tested in PRODUCTION against a real Kroger account.
Kroger publishes a Postman collection and per-environment variable files.

## Acceptable use — read before building an agent

Kroger's Acceptable Use policy explicitly PROHIBITS: adding items to a customer's cart
without their explicit request; comparing Kroger products or prices against other retailers;
systematically scraping responses to build a database; tracking, sharing or storing data
derived from a customer's cart, searches or location; using the profile ID to map or store
customer data; and altering product, price or location values.
https://developer.kroger.com/documentation/public/getting-started/acceptable-use

## Agent surface

- No MCP server (api.kroger.com/mcp → 404, mcp.kroger.com → NXDOMAIN)
- No A2A agent card on any host
- No public OpenAPI: specs are rendered behind the developer-portal login
  (developer.kroger.com/api/v1/developer/contracts/... → HTTP 401)
- No first-party SDK in any language
- Security contact: https://www.kroger.com/.well-known/security.txt →
  The Kroger Co - Vulnerability Disclosure Program on Bugcrowd
